Our infrastructure team is migrating to a hardened deployment model, but our legacy docker-compose.yml files still contain insecure defaults. We have a Java-based CLI tool located at /app/mercury-cli that is supposed to automate this hardening process, but its parsing logic is failing.

Your task is to implement the missing logic in the Java CLI to parse the target compose file and the /app/mercury-cli/compose-images.json lockfile, and output a secure configuration. To determine which services require strict hardening and which are granted exceptions, you must analyze the extensive security audit log provided in /app/docs/mercury-security-dossier.md. The final hardened output must enforce the following rules unless an explicit exception is found in the dossier: strip all non-loopback ports (formatting them strictly as "127.0.0.1:HOST:CONTAINER"), drop privileged capabilities (by adding `cap_drop: ["ALL"]`), enforce image digest pinning using the lockfile (formatting as `image@sha256:digest`), and run the container as a non-root user (strictly outputting the string `"1000"` for the user field). 

Once you have fixed the Java code, compile it using the provided Gradle wrapper and run the CLI against /app/fixtures/docker-compose.yml. The CLI must successfully generate /app/output/hardened-compose.yml containing the sanitized configuration, and /app/output/hardening-report.json. The JSON report must strictly match the following schema: a root object containing two integer fields named `services_processed` and `exceptions_granted`.
